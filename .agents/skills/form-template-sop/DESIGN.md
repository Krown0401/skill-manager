# form-template-sop 设计文档

## 一、背景：从问题到设计

### 1.1 实践暴露的核心问题

在实际通过 AI + Skill 方式完成多家医院表单配置的过程中（涉及 3 家医院、5 张单据），暴露了以下系统性缺陷：

| 问题类别 | 核心矛盾 | 负面影响 |
| --- | --- | --- |
| **前置信息缺失** | 凭证编码、字典集、字段映射表未提前提供，AI 自行编造 | 后期逐一返工对齐，反复修正 |
| **UI 理解偏差** | AI 仅凭截图理解字段，缺乏结构化字段描述文档 | 字段顺序、标题、必填标识需人工逐项验证 |
| **联动边界遗漏** | 多行程判断、空值兜底、列内联动根路径等边缘场景未覆盖 | 部署后才发现逻辑错误，用户感知差 |
| **无校验闭环** | 缺少 JSON 语法、字段名一致性、prop 唯一性等自动检查 | 问题遗漏到用户端，信任度下降 |
| **多轮迭代成本高** | 每次修改需部署验证，修 A 问题引入 B 问题 | 反馈周期长，效率低 |

详细问题汇总参考：[ai生单问题汇总与下一步设计.md](../../../.trae/documents/ai生单问题汇总与下一步设计.md)

### 1.2 根因分析

```
前置信息缺失 ──→ AI 编造字段/编码 ──→ 返工
Skill 知识不足 ──→ 边缘场景遗漏 ──→ 联动逻辑错误
无结构化描述 ──→ AI 凭截图猜测 ──→ 页面偏差
无校验机制 ──→ 问题留到部署 ──→ 用户发现
经验不回写 ──→ 同类问题重复出现 ──→ 效率无提升
```

### 1.3 改进方向

从上述根因出发，确定了两个改进方向：

**方向 A（短期）：增强现有 schema-creator Skill**
- 补充联动模式库、组件配置规范、模板组件索引
- 在已有 SKILL.md 中增加自检清单

**方向 B（长期）：建立标准化 SOP 流程**
- 将"生成过程"标准化，而非仅增强"配置能力"
- 通过"先分析、再确认、后配置"的三段式流程，从源头减少错误
- **这就是本 Skill 的定位**：作为 schema-creator 的上游协作流程

## 二、设计目标

### 2.1 核心目标

建立一套标准化的表单配置 SOP，实现：

1. **信息前置化**：在开始配置前，强制收集所有必要信息（凭证编码、字段映射、字典集、UI 截图）
2. **理解结构化**：通过 AI 分析 UI 截图 + 接口元数据，输出结构化的字段描述文档
3. **确认前置化**：在 AI 动手改 schema 之前，先生成确认文档让人工 Review
4. **可追溯**：每次任务有独立的文件夹，包含完整的分析记录、确认文档、配置产出

### 2.2 与传统方式对比

| 环节 | 传统方式（直接配 schema） | SOP 方式（先分析确认） |
| --- | --- | --- |
| 信息收集 | 口头或零散提供 | 强制启动检查单逐项确认 |
| UI 理解 | AI 凭截图猜测 | AI 调用视觉 API 结构化分析 |
| 人工确认 | 改完 schema 后 Review | 改 schema **前** Review 分析结果 |
| 错误发现 | 部署后用户反馈 | 确认阶段提前拦截 |
| 知识沉淀 | 无固定机制 | 任务文件夹完整归档可追溯 |

## 三、工作流程

### 3.1 六步流程

```
Step 0: 要素收集（Jira 解析）
  └─ 使用 jira-fetcher Skill 获取 Jira 任务信息

Step 1: 整合创建任务文件夹
  └─ 整合要素 + 创建标准化任务目录

Step 2: AI 分析 UI
  └─ AI 看截图，凭视觉理解输出结构化字段清单
  └─ **严格对齐原则**：字段标题必须与截图文本完全一致，禁止任何语义化修正或补全。

Step 3: 接口取数与数据富化 (Data Enrichment)
  └─ 自动登录系统，抓取字段定义与字典，智能比对 UI 字段

Step 4: 生成实施文档 (Spec)
  └─ 深度整合 UI、API 与参考单据（隐藏字段、语法逻辑）
  └─ 形成 `ImplementationSpec.md` 作为 `schema-creator` 的终极指令集

     ── 人工 Review 确认通过 ── 启动配置 ──

Step 5: 对接 OpenSpec（规划中）
  └─ 将确认文档转为 OpenSpec 格式
```

### 3.2 实施文档的核心价值

实施文档（Spec）不仅仅是字段清单，它是「配置契约」：
1.  **解决隐藏字段遗漏**：自动从参考单据中提取 `accountYear`、`recId` 等系统必需字段。
2.  **保留高级语法**：复制参考单据中经过验证的 `x-reactions` 脚本，避免 AI 重写逻辑。
3.  **约束布局细节**：将 Step 2 的 UI 分析结果转化为硬性的 `gridSpan` 指令。
4.  **端到端同步**：同时包含 PC 和移动端的特定组件建议和联动表达式。

## 四、脚本设计

### 4.1 step1-create-task-folder.sh

**用途**：创建标准化的任务目录结构

```
tasks/<任务名>/
├── 原始资料/          # UI 截图、接口文档等原始素材
├── 分析结果/          # AI 分析输出
├── 确认文档/          # 待人工 Review 的确认文档
└── 配置产出/          # 最终 schema 配置产出
```

### 4.2 step2-analyze-ui.py

**用途**：调用 MiniMax API 分析 UI 截图，输出结构化字段清单

- 入参：截图路径、凭证应用编码（可选）
- 处理：
  1. 读取截图文件
  2. 调用 MiniMax API 进行视觉分析
  3. 结构化输出字段清单（JSON）
- 出参：结构化分析结果（JSON）

### 4.3 step3-enrich-data.mjs

**用途**：自动化抓取后端元数据，并与 UI 分析结果进行智能比对。

- **核心逻辑**：
    1.  **自动发现**：根据单据名自动在系统中模糊搜索并锁定 `certCode`。
    2.  **三重比对**：通过 Title (中文名)、Name (代码) 以及 Fuzzy Match 三重算法关联字段。
    3.  **元数据补全**：自动从 API 中提取 `isRequired`、`dictCode`、`componentType` 等核心属性。
    4.  **字典校验**：自动对 UI 上所有选择类组件执行 `get_dictionary` 校验。

### 4.4 step3-generate-confirmation.py

**用途**：结合分析结果 + 用户提供的凭证元数据，生成确认文档

- 入参：分析结果路径、凭证元数据（可选）
- 处理：
  1. 读取分析结果
  2. 合并凭证元数据（字段映射、字典集）
  3. 生成 Markdown 格式确认文档
- 出参：确认文档（.md）

## 五、与现有技能的关系

```
jira-fetcher（独立 Skill）
    │
    │  Step 0：要素收集（Jira 解析）
    ▼
form-template-sop（本 Skill）
    │
    │  Step 1-3：整合创建 + UI 分析 + 确认文档
    ▼
schema-creator（现有 Skill）
    │
    │  依据确认文档生成 form.json 配置
    ▼
schema-organizer（现有 Skill）
    │
    │  批量修改、差异对比、搜索字段
    ▼
最终产出：各院区表单配置
```

**协作模式**：先用 jira-fetcher 获取 Jira 信息，再用 form-template-sop 完成分析确认，最后切换到 schema-creator 进行实际配置。确认文档作为 Skill 之间的契约，确保 AI 在配置阶段有明确的规范依据。
